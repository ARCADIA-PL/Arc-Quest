# Arc Quest 同步策略基线规范 v1（对齐 FTB Quests）

## 1. 文档目的

本规范用于统一 Arc Quest 在 `Quest / Dialogue / Trade / Gacha` 各模块中的同步设计，解决以下长期问题：

- 同步时机分散、策略不一致
- 网络包职责混杂（open / sync / result / failed）
- 客户端 UI 参与业务判断导致状态漂移
- 保存语义与网络同步语义混用

该规范参考了 FTB Quests（1.20.1/dev）中成熟的分层同步思路，并结合 Arc Quest 当前代码现状给出可执行约束。

---

## 2. 总体原则（强约束）

1. **服务端权威**：客户端只展示与请求，不做最终业务裁决。
2. **分层同步**：全量定义、运行态快照、增量事件分层处理。
3. **推送优先，拉取兜底**：状态变更时服务端推送；客户端周期同步仅用于兜底。
4. **变化检测在服务端**：客户端可以高频请求，但服务端仅在状态变化时下发同步包。
5. **网络同步与持久化分离**：`markDirty`、`saveIfChanged/saveNow`、`sync` 语义不可混淆。
6. **UI 只消费快照**：界面不跨层拼状态，不自行“推导最终结论”。

---

## 3. 同步分层模型

### L0：全量定义层（低频）

- 典型场景：登录后首次、资源重载、版本切换
- 内容：配置/定义类数据
- 特征：数据体积大、频率低

### L1：运行态快照层（中频）

- 典型场景：界面打开、界面恢复、手动请求重同步
- 内容：可交互状态（canX、remaining、cooldown、visibility、condition、shortfall）
- 特征：用于“当前界面基准状态”

### L2：增量事件层（高频）

- 典型场景：购买成功、抽奖失败、任务进度变化、奖励领取
- 内容：最小差异字段
- 特征：轻量、实时

---

## 4. 网络包命名与职责规范

### 4.1 C2S

- `C2S<Domain>ControlPacket`：界面控制请求（OPEN/SYNC）
- `C2S<Domain>ActionPacket`：业务操作请求（PURCHASE/DRAW/CLAIM）
- `C2S<Domain>ConfirmPacket`：两阶段确认（仅在需要时）

### 4.2 S2C

- `S2C<Domain>StatePacket`：运行态快照（OPEN/SYNC mode）
- `S2C<Domain>ResultPacket`：成功结果（业务成功回包）
- `S2C<Domain>FailedPacket`：失败回包（reason + shortfall）
- `S2C<Domain>DeltaPacket`：增量更新（可选）

### 4.3 禁止项

- 一个包同时承担“打开界面 + 全量定义 + 全部业务回包”
- UI 通过多个无序包拼接最终权威结论
- 将 OPEN 包用于周期同步（仅允许过渡阶段）

---

## 5. 模块策略矩阵

### 5.1 Trade

- OPEN：`Control(OPEN)` -> `State(OPEN)`
- 周期同步：`Control(SYNC)` -> `State(SYNC)`（服务端变化检测）
- PURCHASE：`Action(PURCHASE)` -> `Result/Failed` + 必要时 `State(SYNC)`

### 5.2 Gacha

- OPEN：`Control(OPEN)` -> `State(OPEN)`
- 预览态同步：`Control(SYNC)` -> `State(SYNC)`（服务端变化检测）
- DRAW：`Action(DRAW)` -> `DrawResult / DrawFailed`
- CONFIRM：`Confirm` -> 发奖 + `State(SYNC)`

### 5.3 Quest

- 登录：L0 全量 + L1 运行态
- 进度变化：优先 L2 增量更新
- 必要时触发 L1 重同步

### 5.4 Dialogue

- 会话状态事件化推送
- 恢复节点属于会话态，不与 Trade/Gacha 缓存混存

---

## 6. 触发时机规范

### 6.1 服务端主动推送（优先）

- 交易成功/失败
- 抽奖确认发奖完成
- 条件可见性变化
- 冷却跨阈值
- 限购跨阈值

### 6.2 客户端请求同步（兜底）

- 界面打开后周期请求（默认 10 tick / 0.5s）
- 结果页返回预览页
- 本地检测到背包变化（可选）

---

## 7. 变化检测规范（服务端）

1. 维度：`player/team + domain + shop/entry`
2. 算法：构造 fingerprint（或 snapshot hash）
3. 策略：
   - 新旧一致：不发包
   - 新旧不一致：发 `State(SYNC)` 并更新缓存
4. OPEN 后写入 baseline，避免紧随其后的冗余 SYNC

---

## 8. 持久化与同步分离规范

- `markDirty()`：仅标记内存状态变化
- `saveIfChanged()/saveNow()`：仅负责落盘
- `sync...()`：仅负责网络传播
- 禁止将“序列化 + 同步 + clearDirty”定义为完整保存

---

## 9. 客户端缓存规范

缓存拆分为两层：

1. **AuthorityState**
   - canX、remaining、cooldown、visibility、condition
2. **UiFeedbackState**
   - failReason、shortfall、toast、shake、tooltip

约束：

- `StatePacket` 更新 AuthorityState
- `FailedPacket` 优先更新 UiFeedbackState
- UI 不跨层读取未定义字段

---

## 10. 可观测性（日志/指标）

必须提供以下统计维度：

- 客户端请求次数（request）
- 服务端实际下发次数（sync sent）
- 变化检测拦截次数（sync dropped）
- 关键链路耗时（open/sync/action/confirm）

### 10.1 SyncTrace stage 统一语义（SYNC-10E/10F）

`SyncObservability.Stage` 固定集合如下：

- `OPEN`：界面打开/首帧快照下发
- `SYNC_REQUEST`：客户端主动发起兜底同步请求
- `SYNC_SENT`：服务端下发了状态快照（变化检测通过）
- `SYNC_DROPPED`：服务端因指纹未变化而拦截同步下发
- `ACTION`：客户端业务动作请求到达服务端（purchase/draw/confirm 等）
- `RESULT`：服务端业务动作结果已产出并回包（success/failed）

约束：

1. Trade/Gacha 的 open、manual sync、action、result 必须打点。
2. push 触发链路至少打 `ACTION`（上游触发）+ `SYNC_SENT/SYNC_DROPPED`（下游结果）。
3. `reason` 字段统一记录触发来源（如 `manual_sync`、`purchase_result`、`delta_progress_sync`）。
4. 禁止新增自由文本 stage 名称，新增语义需先扩展 `Stage` 枚举。

### 10.2 Action Reject Code 统一字典（SYNC-Q2）

- Quest 域引入 `QuestRejectCodeDictionary.Code` 作为 action 失败归因标准。
- Quest C2S action 必须回发 `S2CQuestActionResultPacket`，用于客户端提示与日志对齐。
- action handler 内部禁止仅返回 `boolean` 丢失失败语义；应返回 `Code`。
- 对外兼容层可继续保留 `boolean` 包装（`code == OK`）。
- trace 的 `RESULT` 至少要区分 success/rejected；详细拒绝原因通过 `Code` 与 `errorKey` 记录。
- Dialogue 域同样禁止自由文本 reason，统一收口到 `SyncObservability.Reason` 枚举。

推荐日志键：

- `domain`
- `shopId/entryId`
- `player/team`
- `reason`
- `fpChanged`

---

## 11. 发布前验收（同步维度）

1. 条件/限购/成本变化可在预期窗口（<=0.5s）内反映
2. 成功/失败回包可驱动正确 UI 状态机
3. 不需要“二次点击”触发状态修正
4. 断线重连后状态一致
5. 多玩家/同队情况下状态一致
6. 变化检测命中率明显降低无效同步包

---

## 12. 实施路线建议

### 阶段 A：协议收口

- open/sync 拆分或 mode 合并（语义清晰）
- result/failed 独立保留

### 阶段 B：变化检测

- 服务端按 player+shop 维护 fingerprint baseline
- 引入“无变化不下发”

### 阶段 C：推送优先

- 将关键状态变化点改为服务端主动推送
- 客户端周期同步保留为兜底

### 阶段 D：统一抽象

- Trade/Gacha 刷新与缓存接口统一
- 回归测试模板统一
