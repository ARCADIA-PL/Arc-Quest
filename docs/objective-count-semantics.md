# Objective item matching and effective counts

`ObjectiveItemResolver` defines item identity and item-tag matching for COLLECT, CRAFT, OFFER and DELIVER. Native objective icons and JEI use fresh count-one candidates from this same resolver. A configured tag takes precedence over `targetId`; an invalid, missing or empty tag has no candidates and never falls back to the item ID. NBT and display-name variants of a matching item remain valid; an objective icon is decorative and cannot change its completion target.

The normal event index resolves tags when queried, so an index built before tag loading can still match loaded tags. The per-player tracker rebuilds on server tag updates. Expanded handles include the actual event key in their identity, and phase removal removes the stored handles, including members removed by a tag reload. Collection dispatch uses the same matcher while retaining its own BINARY, ACCUMULATE and UNIQUE_SET entry rules, completion targets, limits and repeatability.

CRAFT remains driven by the existing Forge `PlayerEvent.ItemCraftedEvent`; this change does not infer furnace or third-party machine crafting. Existing CRAFT objectives using `target_tag` now reach the same event index as other item objectives. COLLECT credits successful `PlayerEvent.ItemPickupEvent` quantities, including partial pickups, rather than the amount in a cancellable pre-pickup event. Crafted and picked-up quantities are credited to the periodic inventory snapshot to avoid counting them again; the snapshot includes the menu cursor so moving crafted output into the inventory on a later tick is not a second acquisition.

## Effective quantity

`QuestProgressHandler.resolveRequiredCount` is the shared server calculation. It first evaluates the Java `countModifier` using the real server player, then applies `count_mode` (`fixed`, `level_scale`/`player_level`, or `variable`) and the configured base/min/max. Multiplication and progress increments use wide arithmetic and saturate at the positive integer limit instead of overflowing. Progression truncates against this effective count, not the static definition count. A subsequent matching event also checks completion if a dynamic count has fallen below existing progress.

OFFER and DELIVER inventory matching also uses the shared resolver. Submission resolves its effective threshold before consuming inventory and carries that same value into progression, avoiding a second callback on the changed inventory. The ordinary objective submission service rejects inactive runtimes and collection-profile quests before consumption; collection entries retain their separate progression API.

JEI uses the full calculation. The native client receives the server result through existing full quest, quest-state and delta-progress packets and reads it using `ClientQuestCache.getRequiredCount(questId, phaseId, index, fallback)`. Parallel phases retain separate counts. Full/state sync refresh counts, progress deltas carry the count used for that event, and flag/variable sync plus the existing 20-tick player check refresh count changes without requiring another acquisition. Threshold refresh is a derived-data operation and does not grant rewards or advance phases. Count callbacks should therefore be read-only and deterministic for the same player state.

The client falls back to the definition count only when it has no authoritative runtime count, including an unaccepted quest preview. A preview without a server player does not execute a server-only count callback. Counts retained for completed phases of an active quest preserve their last resolved value; reconstructing historical dynamic counts after the whole quest has been removed is outside this runtime cache.

## Compatibility

The ArcQ network protocol is **16** because quest runtime and delta payloads changed. Both ends must use the matching ArcQ build. This adds no JEI dependency to the common packet model or required-count API. Runtime NBT schema **4** adds `EffectiveRequiredCounts`; older NBT loads without the field and uses the explicit fallback until the server refreshes it. Counts saved with NBT are a cache, not an authoritative replacement for the current resolver. Existing Java delta-packet constructors remain available and encode an unspecified count of zero; native clients then retain their existing count or use the definition fallback.
