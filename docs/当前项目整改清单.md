# Arc Quest 当前项目整改清单

## 1. 文档目的

本文档用于沉淀当前项目在完成本轮 gacha 相关缺陷修复后，真正需要推进的整改事项。

目标不是继续堆叠临时补丁，而是对当前已经暴露出的结构问题、状态同步问题、职责膨胀问题和潜在一致性风险进行收口，避免后续开发继续在不稳定基础上扩张。

---

## 2. 当前项目状态结论

当前项目整体处于“可编译、可测试、核心链路基本可用，但局部复杂度已经明显上升，需要尽快治理”的状态。

### 2.1 当前正面状态

- `compileJava` 已通过
- `test` 已通过
- gacha 的核心现象“确认发奖后返回预览界面仍显示可抽，必须再点一次才变成材料不足”已经定位到根因
- 当前修复已经基本命中该根因：确认发奖后需要立即重新同步权威状态，而不是等待下一次 draw 请求失败后才更新客户端

### 2.2 当前主要问题

- gacha 的网络协议职责开始混杂
- `ClientGachaCache` 状态职责过多，后续极易产生覆盖顺序问题
- `C2SDrawGachaPacket` 的扣费、状态推进、事件派发之间存在潜在事务边界风险
- `QuestCapabilityTickHandler` 当前的“保存”语义并不严格，容易造成错误认知
- trade / gacha 两套 UI 状态管理逻辑已经出现相似扩散趋势，但尚未统一抽象

---

## 3. 整改优先级总览

整改事项按四个级别划分：

- 必做：不做会继续埋雷，或会导致未来反复返工
- 应做：短期不做还能跑，但维护成本会持续升高
- 可做：改善体验或结构质量，但不影响近期稳定性
- 暂缓：现阶段不建议继续投入，否则会干扰主线治理

---

## 4. 必做项

### 4.1 清理当前未提交改动，恢复提交边界

#### 问题

当前工作区仍存在未提交文件，说明当前修复链路还存在“悬空状态”，不利于后续判断哪些改动是稳定结果，哪些改动只是调试残留。

#### 当前已观察到的未提交文件

- `src/main/java/org/com/arc_quest/trade/gacha/network/C2SOpenGachaPacket.java`
- `src/main/java/org/com/arc_quest/client/gui/shop/AbstractTradeScreen.java`

#### 整改要求

- 将与当前 gacha 主修复直接相关的改动单独提交
- 与 trade 相关但尚未完成设计的改动拆出或回滚
- 保证工作区尽快回到 clean 状态

#### 验收标准

- `git status` 无无关残留修改
- 提交记录具备明确主题，不混合 trade / gacha / quest 的不同目标

---

### 4.2 拆分 gacha 的“打开界面”和“状态同步”协议职责

#### 问题

当前 `S2COpenGachaPacket` 已经同时承担：

- 打开界面
- 刷新权威状态
- 覆盖抽奖历史
- 注入支付不足 shortfall 信息
- 在界面已打开时只刷新 preview 而不重开 screen

这说明它已经不是单纯的“open packet”，而是“open + resync”的混合体。

#### 风险

- 名称与职责不一致
- 后续维护时容易误改
- 极易再次混淆 `C2SOpenGachaPacket`、`C2SConfirmDrawPacket`、`S2COpenGachaPacket` 的职责边界

#### 整改要求

建议拆为两类包：

1. `S2COpenGachaPacket`
   - 只负责首次打开抽奖界面
2. `S2CSyncGachaStatePacket`
   - 只负责同步权威状态快照
   - 包含至少以下内容：
     - `canDraw`
     - `remainingDraws`
     - `pityCounter`
     - `totalDraws`
     - cooldown 相关字段
     - shortfall / failReason（按需要设计）

#### 配套调整

- `C2SConfirmDrawPacket` 成功发奖后发送 sync 包，而不是再次走 open 包语义
- `GachaScreen` 中收到 sync 时只刷新缓存和 preview，不触发 screen 生命周期逻辑

#### 验收标准

- 确认发奖后回到 preview 时，按钮第一时间显示正确状态
- 协议语义清晰：open 就是 open，sync 就是 sync
- 后续日志排查时能快速区分“首次打开”和“状态刷新”

---

### 4.3 拆分 `ClientGachaCache` 的职责

#### 问题

当前 `ClientGachaCache` 同时管理：

- pity / totalDraws
- canDraw / remainingDraws
- cooldown
- draw history
- last fail reason
- shortfall
- 最近一次抽中结果
- 可能与 UI 反馈联动的辅助状态

这类结构在短期修 bug 时方便，但中长期极易演变成“万能缓存类”。

#### 风险

- 权威状态与 UI 反馈状态相互污染
- open / result / failed / confirm sync 的覆盖顺序变得难以追踪
- 任何一个字段更新时机出错，都会产生局部不同步问题

#### 整改要求

至少在数据职责上拆成两类：

1. 权威状态（Authority State）
   - pityCounter
   - totalDraws
   - canDraw
   - remainingDraws
   - cooldown 数据
   - resetTime 等

2. UI 反馈状态（Feedback State）
   - lastFailReason
   - shortfall
   - 最近一次提示性结果
   - 仅供预览提示或局部交互反馈使用的数据

#### 验收标准

- `updateSessionWithHistory(...)` 不再顺便修改失败提示态
- `recordDrawFailure(...)` 不再污染权威快照
- `GachaPreviewPanel` 读取的是明确的 snapshot 对象，而不是零散字段拼装

---

### 4.4 重新定义 `C2SDrawGachaPacket` 的事务边界

#### 问题

当前 draw 链路中：

- `PreDrawEvent` 在锁外执行
- `drawCost.canAfford(...)` 在锁外执行
- `drawCost.execute(...)` 在锁外执行
- 真正的抽奖状态推进在锁内执行
- 事件派发 / 发包 / 日志又放在锁外执行

这种结构虽然缩小了锁范围，但同时也削弱了扣费、状态推进、结果写入之间的一致性保障。

#### 风险

- 理论上可能出现“扣费成功，但抽奖状态推进失败”的破口
- `PreDrawEvent` 修改 pityCounter 后，到锁内消费之间存在窗口
- 如果未来有更多扩展事件，语义会继续变得脆弱

#### 整改要求

必须明确采用以下两种路线之一，不可长期悬而不决：

##### 路线 A：恢复保守事务边界

将以下关键步骤放进同一个原子执行域：

- 扣费执行
- 抽奖结果生成
- pity / drawCount / cooldown 更新
- pending 结果写入

##### 路线 B：建立补偿机制

如果继续保持扣费在锁外，就必须保证：

- 锁内推进失败时有明确补偿机制
- 补偿逻辑可追踪、可验证
- 不能出现吞费无结果

#### 验收标准

- 通过人工注入失败路径或异常场景验证：不会出现扣费后无结果
- draw 成功 / 失败 / 扣费 / pending / 发包日志可以形成完整闭环

---

## 5. 应做项

### 5.1 将状态计算从 `GachaScreenOpener` 中抽离

#### 问题

当前 `GachaScreenOpener` 同时负责：

- 对话恢复目标节点管理
- 会话初始化
- reset 逻辑
- canDraw 与 shortfall 计算
- 组装网络包
- 发包

职责偏多，后续 open 与 sync 都依赖这里，会越来越重。

#### 整改要求

新增统一的状态解析层，例如：

- `GachaStateSnapshotResolver`
- `GachaStateAssembler`

专门负责从 `player + shop + cap` 计算出权威快照。

#### 验收标准

- open 与 sync 复用同一份状态计算逻辑
- `GachaScreenOpener` 回归“流程调度器”角色

---

### 5.2 增加 gacha 核心回归验证清单

#### 问题

当前很多问题是靠人工日志定位出来的，说明缺少一套最小稳定回归场景。

#### 整改要求

至少建立以下三类验证：

1. **材料刚好耗尽场景**
   - 第一次抽成功
   - confirm 后回到 preview
   - 按钮立即显示不足，不需要再点一次

2. **失败回包回退场景**
   - draw 请求失败后，界面从 waiting 正确退回 preview

3. **冷却 / 剩余次数边界场景**
   - cooldown 生效时 UI 直接显示冷却提示
   - 剩余次数为 0 时直接不可抽

#### 验收标准

- 每次修改 gacha 网络包或客户端缓存后，都能快速复测
- 不再依赖“再次点一次看会不会刷新”这种人工碰运气方式

---

### 5.3 单独治理 QuestCapability 的持久化语义

#### 问题

当前 `QuestCapabilityTickHandler` 内部使用：

- `serializeNBT().copy()`
- 写入 `player.getPersistentData()`
- 再执行 `syncFullData`
- 然后 `clearDirty()`

这更像“防抖同步器”，而不是严格意义上的持久化保存。

#### 风险

- 容易让人误以为 capability 已经完成可靠存档
- 后续如果出现重登、切维度、异常退出后的数据一致性问题，会很难排查

#### 整改要求

- 明确区分“同步”和“持久化保存”两个概念
- 将当前逻辑的命名、日志和注释调整为真实语义
- 评估并补齐真正的持久化链路

#### 验收标准

- 代码中不再把 `persistentData + sync + clearDirty` 描述为真正 save
- 数据落盘逻辑与网络同步逻辑边界清晰

---

## 6. 可做项

### 6.1 统一 trade / gacha 的短缺提示与 snapshot UI 模式

#### 现象

当前 trade 与 gacha 已经都出现：

- shortfall tooltip
- failReason
- snapshot 驱动按钮状态
- waiting / failed / rollback 这类 UI 状态机

#### 整改建议

提取共性抽象，例如：

- 权威快照接口
- 失败反馈接口
- 统一的短缺提示渲染逻辑

#### 价值

- 降低复制粘贴
- 避免 trade 和 gacha 行为逐渐偏离

---

### 6.2 精简 gacha 网络包载荷

#### 现象

当前 open 包中承载了较多数据，包括历史记录和 shortfall 信息。

#### 建议

- history 可考虑单独同步或限制字段规模
- 明确哪些字段属于首次打开必须，哪些字段属于局部刷新需要

#### 价值

- 降低协议复杂度
- 让调试更清晰

---

## 7. 暂缓项

### 7.1 暂缓进一步 UI 视觉层优化

在状态同步协议和缓存职责未收口前，不建议继续通过视觉补丁来掩盖状态源问题。

原因：

- 会增加排障噪音
- 容易造成“看起来修好了，其实只是更不明显了”的错觉

---

### 7.2 暂缓继续扩展 dialogue 与 gacha / trade 的跨系统跳转能力

当前 restore 路径虽然可用，但已经具备明显复杂度。此时继续扩展更多跨系统跳转，会让 restore 语义进一步变重。

建议先把 gacha 的 open / sync / rollback 主线稳定，再继续扩 dialogue 联动能力。

---

## 8. 推荐执行顺序

如果按最务实的方式推进，建议按以下顺序执行：

### 第一步：整理工作区

- 提交或回滚当前未提交文件
- 恢复 clean workspace

### 第二步：拆分 gacha open / sync 协议

- 引入 `S2CSyncGachaStatePacket`
- 让 confirm 成功后走 sync，不再复用 open

### 第三步：拆分 `ClientGachaCache`

- 权威状态和 UI 反馈状态分离
- 明确 snapshot 的来源和消费路径

### 第四步：复审 `C2SDrawGachaPacket` 的事务设计

- 明确扣费、状态推进、pending、发包的事务边界
- 决定采用“收回原子域”还是“显式补偿机制”

### 第五步：补充最小回归验证清单

- 围绕 gacha 三个核心场景固定回归路径

---

## 9. 最终结论

当前项目真正需要的，不是继续堆叠临时补丁，也不是立刻继续扩展新功能。

真正需要的是先完成以下三件事：

1. 收口 gacha 的网络协议职责
2. 收口客户端缓存职责
3. 收口 draw 事务边界

只有这三件事处理完，当前这轮 gacha 相关修复才算真正进入稳定阶段。否则后续继续开发时，trade、dialogue、quest 保存、gacha UI 都会继续互相牵连，排障成本会越来越高。

---

## 10. SYNC-10 计划草案（自动化回归 + 发布前检查脚本）

### 10.1 目标

将“人工可执行回归清单”升级为“可重复、可门禁、可追责”的自动化检查基线，确保同步语义不回退。

### 10.2 本期范围

1. 自动化同步专项（最小集合）
   - 场景 A：材料刚好耗尽（Gacha）
   - 场景 B：Quest 条件变化触发 Trade/Gacha push
   - 场景 C：冷却边界切换
   - 场景 D：断线重连恢复一致性
2. 发布前检查脚本（pre-release sync check）
   - 编译检查
   - 核心日志/拒绝码检查
   - 关键场景 smoke 结果汇总

### 10.3 交付物

1. 自动化测试入口（建议）
   - 在 `src/test/.../sync/` 下建立同步专项测试套件
   - 每个场景至少 1 个 happy path + 1 个 fail path
2. 发布前检查脚本（建议）
   - `scripts/pre_release_sync_check.(ps1|sh)`（按平台）
   - 输出统一结果摘要（PASS/FAIL + 失败项）
3. 结果产物
   - `build/reports/sync-check/summary.txt`（或等价）
   - 关键日志片段（request/sent/dropped + reject code）

### 10.4 验收标准（DoD）

1. `compileJava` 通过
2. 四个同步关键场景自动化可运行且结果稳定
3. 脚本一次执行可给出明确门禁结论（可接 CI）
4. 至少一条拒绝码链路完成“服务端日志 -> 客户端反馈”的自动校验
5. Gap List 与整改清单更新到 SYNC-10 口径

### 10.5 任务拆解

#### SYNC-10.1 自动化用例骨架

- 建立同步测试基类（启动、玩家上下文、日志采集）
- 建立场景 A/B/C/D 的用例骨架
- 先让测试“能跑起来”并可稳定读取断言数据

#### SYNC-10.2 场景断言完善

- A：draw 后 canDraw/shortfall 立即变化
- B：quest 更新后 active screen 收到 push（sent 或 dropped 有据）
- C：冷却跨边界状态正确切换
- D：重连后 authority 与客户端缓存一致

#### SYNC-10.3 发布前检查脚本

- 步骤：
  1) 编译
  2) 运行同步专项（可选子集）
  3) 抽取关键日志指标（request/sent/dropped/reject）
  4) 输出摘要并返回退出码
- 退出码策略：
  - 全部通过返回 0
  - 任一关键项失败返回非 0

#### SYNC-10.4 文档与门禁接入

- 更新 Gap List（状态、阶段映射、剩余项）
- 更新整改清单中的“发布前执行步骤”
-（可选）接入 CI job，先非阻塞后阻塞

### 10.6 风险与缓解

1. 测试环境时序不稳定（尤其冷却边界）
   - 缓解：引入可控时钟或统一时间推进策略
2. 日志断言脆弱
   - 缓解：优先断言结构化字段（模块/动作/结果/拒绝码）
3. 改动范围扩大影响主干
   - 缓解：先最小集成（骨架+关键四场景），再逐步扩展
