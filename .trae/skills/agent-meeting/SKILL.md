# Agent Meeting — 多 SubAgent 研讨协议

> 快捷召集指令，支持 5 种研讨模式。多轮交叉质询后输出总结。

## 触发词

以下任意触发词均可激活此技能：

| 触发词 | 示例 |
|--------|------|
| `@meeting code` | `@meeting code NPC编辑器数据绑定问题` |
| `@meeting design` | `@meeting design 对话编辑器交互流程` |
| `@meeting review` | `@meeting review DialogueTreeBuilder 重构方案` |
| `@meeting all` | `@meeting all 跨模式导入路由设计` |
| `@meeting perf` | `@meeting perf FTB Quests 大规模 quest 性能瓶颈分析` |
| `/meeting code\|design\|review\|all\|perf` | `/meeting perf 事件处理热路径对比` |
| `召集研讨` | `召集研讨 perf 跨项目架构性能审计` |
| `双方对撞` | `双方对撞 field naming` |

## 模式 1：`code` — 代码方 vs 编辑器方双边对撞

**适用场景**：架构设计、API 对齐、数据格式协商、字段命名、序列化行为、校验规则

**角色**：

| 角色 | 立场 | 关注维度 |
|------|------|----------|
| **代码方** | Java Spec / Compiler / Validator / Runtime | 确保编辑器输出能通过编译、Validator 不报错、运行时正确 |
| **编辑器方** | JS state / factories / renderers / editors | 确保编辑器可用、补全准确、交互流畅、不产出错误格式 |

**流程**：

1. **Agent 先深读两端代码**：Java 端（编译器/校验器/Spec 类）和编辑器端（state/renderers/import-export）
2. **第 1 轮**：双方陈述需求与立场（各自列出关键约束和疑问）
3. **第 2 轮**：交叉质询（双方互相提问，可否定对方假设）
4. **第 3 轮**：代码方最终回应 + 合意裁决
5. **输出**：议题清单 + 裁决列表 + 施工建议（必须逐条编号，含理由）

**输出格式**：

```markdown
# {议题} — 代码方 vs 编辑器方研讨总结

## 参与方
| 角色 | 代表 |
|------|------|
| 代码方 | {具体 Spec/Compiler 类名} |
| 编辑器方 | {具体模块/文件名} |

## 裁决清单
| # | 议题 | 裁决 | 理由 |
|---|------|------|------|
| 1 | ... | ... | ... |

## 变更文件清单
## 施工建议
```

## 模式 2：`design` — 设计师团队评审

**适用场景**：UX 评审、界面重构、交互优化、布局调整、视觉层次

**角色**（4 人固定阵容）：

| 代号 | 角色 | 关注维度 |
|------|------|----------|
| **Leah** | 信息架构师 | 导航结构、层级、可发现性 |
| **Ren** | 交互设计师 | 点击模式、状态跃迁、反馈、焦点管理 |
| **Sasha** | 视觉设计师 | 布局、间距、视觉层次、可读性、信息密度 |
| **Marcus** | 系统设计师 | 数据绑定一致性、state 管理、组件复用、重构成本 |

**流程**：

1. **Agent 先审查全部相关 UI 代码**：渲染函数、事件绑定、CSS、state 模型
2. **第 1-3 轮**：发现问题（每人从自己维度列出现有问题）
3. **第 4-6 轮**：提出方案（每人贡献改进方案，互相否定不合理的）
4. **第 7-9 轮**：整合收敛（合并各方方案形成统一草案）
5. **第 10 轮**：最终分歧裁决
6. **输出**：问题诊断清单（含严重度）+ ASCII 布局设计 + 重构文件清单 + UX 决策速查

**输出格式**：

```markdown
# {议题} — 4 人设计师团队 UX 评审

## 参与设计师
{四人代号 + 角色}

## 问题诊断
| # | 问题 | 严重度 | 发现者 |
|---|------|--------|--------|

## 新布局设计（ASCII 图）
## state 模型变更
## 重构文件清单
## 设计决策速查
| # | 决策 | 理由 |
|---|------|------|
```

## 模式 3：`all` — 全栈多角色研讨

**适用场景**：跨层重大决策、全链路架构变更

**角色**：

| 角色 | 关注维度 |
|------|----------|
| **代码方** | Java Spec / Compiler / Validator |
| **编辑器方** | JS state / renderers / editors |
| **设计师** | UX / 交互 / 视觉 |
| **系统设计师** | 重构成本 / state 管理 / 组件复用 |

**流程**：

1. **Agent 先深读全链路代码**：Java Spec → Compiler → Validator → JSON 序列化 + 编辑器 → state → renderers → CSS
2. **第 1-2 轮**：各方陈述（按视角列出需求和约束）
3. **第 3-4 轮**：交叉质询（自由质疑，可否定）
4. **第 5 轮**：系统设计师核算重构成本
5. **第 6 轮**：整合提案 + 最终裁决
6. **输出**：综合裁决 + 架构图 + 施工阶段

## 模式 4：`review` — 纯代码侧多角色代码评审

**适用场景**：Java 端架构重构、编译器链路优化、运行时性能分析、Spec 设计评审、Mixin 安全性审查、API 设计一致性

**角色**（4 人固定阵容，全 Java 侧）：

| 代号 | 角色 | 关注维度 |
|------|------|----------|
| **Spec** | 数据结构设计者 | 字段语义正确性、JSON 序列化兼容、datapack 规范一致性、向前/向后兼容 |
| **Compiler** | 编译链实现者 | 校验链完整度、编译正确性、错误信息可读性、空值 safety、循环依赖检测 |
| **Runtime** | 运行时执行者 | 线程安全、性能热点、内存泄漏风险、状态一致性、reload 后残留状态 |
| **Integrate** | 集成/网络层 | 网络包序列化、客户端-服务端同步、Mixin 注入安全性、事件订阅正确性 |

**流程**：

1. **Agent 先深读全部相关 Java 代码**：Spec 类 → Compiler → Validator → Runtime → Network → Mixin
2. **第 1-2 轮**：各方从各自维度诊断问题（每人列出发现 + 严重度）
3. **第 3-4 轮**：方案提出（每人贡献改进方案，互相否定不合理的）
4. **第 5 轮**：Integrate 核算改动波及面（哪些下游模块受影响、是否需要协调编辑器方）
5. **第 6 轮**：最终裁决 + 施工排序
6. **输出**：问题诊断清单 + 裁决列表（含波及面评估） + 施工顺序建议

**输出格式**：

```markdown
# {议题} — 纯代码侧 4 角色评审

## 参与角色
| 代号 | 角色 | 关注维度 |
|------|------|----------|
| Spec | 数据结构设计者 | ... |
| Compiler | 编译链实现者 | ... |
| Runtime | 运行时执行者 | ... |
| Integrate | 集成/网络层 | ... |

## 问题诊断
| # | 问题 | 严重度 | 发现者 | 波及面 |
|---|------|--------|--------|--------|
| 1 | ... | ERROR/WARN/INFO | Compiler | Spec + Runtime |

## 裁决清单
| # | 议题 | 裁决 | 理由 | 施工优先级 |
|---|------|------|------|-----------|
| 1 | ... | ... | ... | P0/P1/P2 |

## 波及面评估
| 模块 | 受影响 | 说明 |
|------|--------|------|

## 变更文件清单
## 施工顺序建议
```

## 模式 5：`perf` — 多维度性能分析师团队

**适用场景**：项目内性能架构评估、跨项目性能对标、热路径审计、内存/网络/规模化分析、瓶颈定位与排序

**角色**（4 人固定阵容）：

| 代号 | 角色 | 关注维度 |
|------|------|----------|
| **Hotpath** | 热路径分析师 | Tick/Event 热路径、O(N)/O(N²) 遍历模式、缓存命中率、锁竞争 |
| **Memory** | 内存分析师 | 对象分配速率、GC 压力、集合选型 (FastUtil vs JDK)、数据结构紧凑度、内存泄漏风险 |
| **Network** | 网络分析师 | 包大小与频率、序列化格式 (NBT/VarInt/JSON)、登录/同步带宽、双端状态一致性 |
| **Scale** | 规模化分析师 | 数据量增长时的性能退化曲线 (100→1000→10000)、架构天花板、水平扩展能力 |

**流程**：

1. **Agent 先深读全部相关代码**：Spec 定义 → 运行时热路径 → 网络包 → 持久化 → 集合选型
2. **第 1-2 轮**：各方从各自维度诊断问题（每人列出发现 + 严重度 + 量级估算）
3. **第 3-4 轮**：交叉质询（质疑对方数据、补充遗漏热点、提出替代方案）
4. **第 5 轮**：Scale 核算规模退化曲线（给出 N=100/1000/5000 三级评分）
5. **第 6 轮**：最终裁决 + 瓶颈排序 + 优化施工优先级
6. **输出**：瓶颈排名表 + 规模退化表 + 裁决清单 + 施工建议

**输出格式**：

```markdown
# {议题} — 4 维性能分析师审计

## 参与分析师
| 代号 | 角色 | 关注维度 |
|------|------|----------|
| Hotpath | 热路径分析师 | ... |
| Memory | 内存分析师 | ... |
| Network | 网络分析师 | ... |
| Scale | 规模化分析师 | ... |

## 瓶颈排名
| 排名 | 瓶颈 | 触发频率 | 量级 (N=1000) | 发现者 | 严重度 |
|:---:|------|------|:---:|------|:---:|
| 1 | ... | 每 tick/player | 5000 ops/s | Hotpath | 🔴 |

## 规模退化曲线
| 规模 | 综合评分 | 瓶颈变化 |
|------|:---:|------|
| N=100 | 9/10 | 无感知 |
| N=1000 | 7/10 | O(N) 路径显现 |
| N=5000 | 3/10 | O(N²) 组合爆炸 |

## 裁决清单
| # | 议题 | 裁决 | 理由 | 施工优先级 |
|---|------|------|------|-----------|
| 1 | ... | ... | ... | P0/P1/P2 |

## 跨项目对标 (可选)
| 维度 | 项目 A | 项目 B | 优势方 |
|------|:---:|:---:|:---:|
| 事件路由 | O(N) collect() | O(1) index.find() | B |

## 变更文件清单
## 施工顺序建议
```

**跨项目评估特殊规则**：当议题涉及两个项目对比时，Agent 必须同时深读两个项目的等价代码路径（如 FTB 的 `collect()` vs Arc 的 `ObjectiveTypeIndex.find()`），Scale 角色额外产出规模退化对比表。

## 通用规则

1. **必须先深读代码**：研讨开始前，Agent 必须先完整阅读相关 Java 源文件和 JS 源文件，不能凭印象讨论。
2. **MUST 否定**：双方必须积极质疑对方假设。不允许单纯的"Yes, agree"。
3. **逐条编号**：所有裁决必须 `#1, #2, #3...` 连续编号，含明确理由。
4. **输出到蓝图或会议记录**：研讨总结应写入 `BLUEPRINT.md`（施工类）或 `MEETING_MINUTES.md`（记录类）。
5. **构建验证**：如果研讨涉及施工决策，研讨后应执行 `./gradlew compileJava` 验证。
