# Agent Meeting — 多 SubAgent 研讨协议

> 快捷召集指令，支持 3 种研讨模式。多轮交叉质询后输出总结。

## 触发词

以下任意触发词均可激活此技能：

| 触发词 | 示例 |
|--------|------|
| `@meeting code` | `@meeting code NPC编辑器数据绑定问题` |
| `@meeting design` | `@meeting design 对话编辑器交互流程` |
| `@meeting all` | `@meeting all 跨模式导入路由设计` |
| `/meeting code\|design\|all` | `/meeting design 左侧栏树结构` |
| `召集研讨` | `召集研讨 code 方和编辑方讨论` |
| `双方对撞` | `双方对撞 field naming` |

---

## 模式 1：`code` — 代码方 vs 编辑器方双边对撞

**适用场景**：架构设计、API 对齐、数据格式协商、字段命名、序列化行为、校验规则

**角色**：

| 角色 | 立场 | 关注维度 |
|------|------|----------|
| **代码方** | Java Spec / Compiler / Validator / Runtime | 确保编辑器输出能通过编译、Validator 不报错、运行时正确 |
| **编辑器方** | JS state / factories / renderers / editors | 确保编辑器可用、补全准确、交互流畅、不产出错误格式 |

**流程**：

1. **Agent 先深读两端代码**：Java 端（编译器/校验器/Spec 类）和编辑器端（state/renderers/import-export）
2. **第 1 轮**：双方陈述需求与立场（各自列出关键约束和疑问）
3. **第 2 轮**：交叉质询（双方互相提问，可否定对方假设）
4. **第 3 轮**：代码方最终回应 + 合意裁决
5. **输出**：议题清单 + 裁决列表 + 施工建议（必须逐条编号，含理由）

**输出格式**：

```markdown
# {议题} — 代码方 vs 编辑器方研讨总结

## 参与方
| 角色 | 代表 |
|------|------|
| 代码方 | {具体 Spec/Compiler 类名} |
| 编辑器方 | {具体模块/文件名} |

## 裁决清单
| # | 议题 | 裁决 | 理由 |
|---|------|------|------|
| 1 | ... | ... | ... |

## 变更文件清单
## 施工建议
```

## 模式 2：`design` — 设计师团队评审

**适用场景**：UX 评审、界面重构、交互优化、布局调整、视觉层次

**角色**（4 人固定阵容）：

| 代号 | 角色 | 关注维度 |
|------|------|----------|
| **Leah** | 信息架构师 | 导航结构、层级、可发现性 |
| **Ren** | 交互设计师 | 点击模式、状态跃迁、反馈、焦点管理 |
| **Sasha** | 视觉设计师 | 布局、间距、视觉层次、可读性、信息密度 |
| **Marcus** | 系统设计师 | 数据绑定一致性、state 管理、组件复用、重构成本 |

**流程**：

1. **Agent 先审查全部相关 UI 代码**：渲染函数、事件绑定、CSS、state 模型
2. **第 1-3 轮**：发现问题（每人从自己维度列出现有问题）
3. **第 4-6 轮**：提出方案（每人贡献改进方案，互相否定不合理的）
4. **第 7-9 轮**：整合收敛（合并各方方案形成统一草案）
5. **第 10 轮**：最终分歧裁决
6. **输出**：问题诊断清单（含严重度）+ ASCII 布局设计 + 重构文件清单 + UX 决策速查

**输出格式**：

```markdown
# {议题} — 4 人设计师团队 UX 评审

## 参与设计师
{四人代号 + 角色}

## 问题诊断
| # | 问题 | 严重度 | 发现者 |
|---|------|--------|--------|

## 新布局设计（ASCII 图）
## state 模型变更
## 重构文件清单
## 设计决策速查
| # | 决策 | 理由 |
|---|------|------|
```

## 模式 3：`all` — 全栈多角色研讨

**适用场景**：跨层重大决策、全链路架构变更

**角色**：

| 角色 | 关注维度 |
|------|----------|
| **代码方** | Java Spec / Compiler / Validator |
| **编辑器方** | JS state / renderers / editors |
| **设计师** | UX / 交互 / 视觉 |
| **系统设计师** | 重构成本 / state 管理 / 组件复用 |

**流程**：

1. **Agent 先深读全链路代码**：Java Spec → Compiler → Validator → JSON 序列化 + 编辑器 → state → renderers → CSS
2. **第 1-2 轮**：各方陈述（按视角列出需求和约束）
3. **第 3-4 轮**：交叉质询（自由质疑，可否定）
4. **第 5 轮**：系统设计师核算重构成本
5. **第 6 轮**：整合提案 + 最终裁决
6. **输出**：综合裁决 + 架构图 + 施工阶段

---

## 通用规则

1. **必须先深读代码**：研讨开始前，Agent 必须先完整阅读相关 Java 源文件和 JS 源文件，不能凭印象讨论。
2. **MUST 否定**：双方必须积极质疑对方假设。不允许单纯的"Yes, agree"。
3. **逐条编号**：所有裁决必须 `#1, #2, #3...` 连续编号，含明确理由。
4. **输出到蓝图或会议记录**：研讨总结应写入 `BLUEPRINT.md`（施工类）或 `MEETING_MINUTES.md`（记录类）。
5. **构建验证**：如果研讨涉及施工决策，研讨后应执行 `./gradlew compileJava` 验证。
